# 윷 모으기 시작 지연

> 현재 대상은 **Yut**이다.

**상태: 검증 대기 · 우선순위: 높음 · 갱신: 2026-11-12**

사용자는 **윷 모으기 버튼을 누른 뒤 모션의 첫 화면이 나타나기 전 버벅임**을 제보했다. 시작 경로의 이미지·효과음 준비와 중복 장면 갱신을 줄였다. 실기기에서 원인별 소요 시간과 개선 정도는 아직 측정하지 않았다.

## 현재 Yut 모으기 끊김 분석 — 2026-11-11

**2026-11-12 수정 반영 · 실기기 검증 대기.** 사용자는 원본 Yut에는 없던 버튼 직후 끊김을 제보했다. 원본에도 있던 이미지 로더만 회귀 원인으로 단정하지 않고, 새 상태 연결 경로의 중복 처리부터 줄였다.

| 확인한 사실 | 이번 수정 | 검증·한계 |
| --- | --- | --- |
| PlayViewModel이 같은 상태를 render 후 resumePhase에서 다시 render | 상태 반영은 1회, 이후 필요한 센서 준비만 수행. ARCoordinator도 같은 상태·권한·모델의 재적용 생략 | 모으기 상태 1회에 render 1회·효과음 1회 회귀 통과 |
| 단계만 바뀌어도 GameManager가 말·플레이어 배열 재구성 | 말·플레이어·선택이 같으면 스냅샷만 갱신. 반복 stop 호출·동일 AR 표시 값 발행 축소 | 말 이동·재선택·권한 변경·골인·승리 기존 및 신규 회귀 통과 |
| body에서 PNG 파일을 동기 로드. 이 구조는 원본에도 존재 | AR 준비 때 압축 데이터 30장을 읽고 처음 3장·마지막 1장만 비동기 표시 준비. 나머지는 표시할 때 비동기 준비 | 첫 이미지·마지막 대기 화면 준비, 반복 준비 시 객체 재사용, 초기화 시 해제 확인 |
| Timer가 뷰 수명과 분리돼 재생 종료 전 퇴장해도 남을 수 있음 | 취소 가능한 View.task로 원본 30장·30fps 진행. 지연 시 경과 시간에 맞춰 프레임 선택 | 화면 제거 시 준비·대기 작업 취소. 실제 첫/반복 프레임 시간은 미측정 |
| 큰 이미지 전체 디코딩 캐시는 메모리 부담 | 상시 준비 4장만 캐시하고 나머지는 현재 표시용만 유지. 마지막 대기 이미지도 같은 캐시 사용 | 4장 RGBA8 규모 약 25.5MiB + 압축 데이터 약 9.9MiB. 실제 UIKit/GPU 최대 메모리는 별도 실측 |

모으기 1.3초 게임 단계·효과음 속도·원본 PNG 해상도·투명도·윷 3D 투사와 판정은 유지했다. 참가자의 호스트 승인 대기도 기존 권한 규칙을 유지한다. **자동 흐름 통과는 실기기 끊김 해소나 발열 감소율의 근거가 아니다.**

검증: 전체 회귀 **74개 / 14개 suite**, 배치→모으기→수동 던지기 UI **1개 통과**. 시뮬레이터의 마지막 대기 이미지·투명 배경·말판 유지 캡처 확인. iOS·iOS Simulator 빌드 결과와 상세 범위는 [AR 부하 QA](../ar/ar-overheating.md)에 함께 기록한다. 결과: `/tmp/yut-thermal-validation-tests.xcresult`.

다음은 iPhone 15 Pro의 같은 Release 조건에서 첫 실행·반복 10회·복귀 후 입력→화면 표시 지연, 메인 스레드, 프레임·최대 메모리를 측정한다. 단독/호스트/참가자를 구분한다. `GatherInput`→`GatherViewReady` signpost는 뷰 준비 경로이고 실제 화면 표시 완료는 프레임 기록으로 확인한다.
